## 2. 핵심 결정

| 결정 | 선택 | 이유 |
|---|---|---|
| 저장 구조 | 방 전체 한 덩어리 → **메모 1개 = 서버 1줄** (`room_msgs`) | 여러 명이 동시에 써도 서로 덮어쓰지 않음. 지금 구조는 방 전체를 통째로 저장하고 기기에서 합친다 📁 `merge3` |
| 작성자 | 서버가 `author`(처음 쓴 사람)·`edited_by`(마지막 고친 사람)를 **자동으로** 기록 | 앱이 보내는 값을 믿지 않으므로 조작 불가. **2바퀴 기여 기록의 바탕이 1바퀴에서 공짜로 생김** |
| 권한 | '보기만'을 **서버 정책**(`can_write`)에서 막음 | 지금은 화면에서만 막는다 📁 `isRO` |
| 참여 | `join_room(코드, 이름)` 함수로만 참여. 10분에 10번 넘게 틀리면 차단 | 멤버가 아니면 방을 볼 수 없으니, 코드 확인은 서버 함수가 대신함. 코드 맞히기 공격 방지 |
| 나가기 | 내 멤버 줄을 지움. 마지막 사람이 나가면 방도 삭제 | 기획 T7 |
| 사진·파일 | `files` 저장소의 `r/방ID/파일ID` 경로. 방 멤버만 읽기, 쓸 수 있는 멤버만 올리기 | 지금은 `내ID/파일ID`라 본인만 읽음 📁 `index.html` 1598·1699 |
| 반영 방식 | 실시간 구독 + 앱을 다시 열거나 화면이 켜질 때 '바뀐 것만 받기' | 실시간 연결이 끊겨도 놓치지 않게 |
| 개인 메모 | **그대로** (기존 `kv` 표) | 1바퀴 범위 밖. 건드릴수록 위험 |

## 3. 서버 구조 (요약 — 전체는 `supabase/rooms.sql`)

```
rooms         id · code(6자리, 고유) · name · owner · perm(edit/view)
room_members  room_id · user_id · display_name · role(owner/member) · joined_at
room_msgs     room_id · id(앱 메모 ID) · data(메모 객체 그대로) · author · edited_by · deleted · updated_at
```

| 누가 | rooms | room_members | room_msgs | 사진 `r/방ID/…` |
|---|---|---|---|---|
| 방 멤버 | 읽기 | 목록 읽기, **내 이름만** 수정, **나만** 나가기 | 읽기 | 읽기 |
| 쓰기 가능 멤버(함께 수정 방 or 방장) | – | – | 쓰기·고치기·삭제 표시 | 올리기 |
| 방장 | 이름·권한 수정 | – | – | – |
| 멤버 아님 | ✗ | ✗ | ✗ | ✗ |

## 4. 앱 코드 변경 계획 (`index.html`)

**원칙: 화면 코드는 최대한 그대로 두고, 저장·동기화 층에서 갈아 끼운다.**
화면은 지금처럼 이 기기의 `s:room:코드` 사본을 읽고 쓴다. 새로 만드는 `RoomSync`가 그 사본과 서버 `room_msgs`를 맞춘다.

| # | 위치 📁 | 변경 |
|---|---|---|
| C1 | `syncable` (1505줄 부근) | `s:room:` 키는 기존 kv 동기화에서 **빼기** (RoomSync가 담당) |
| C2 | 새 `RoomSync` 모듈 | ① 올리기: 방 사본을 '마지막으로 맞춘 모습'(기존 `hs()` 지문 재사용)과 비교해 바뀐 메모만 `room_msgs`에 upsert, 사라진 메모는 `deleted=true` ② 받기: `updated_at`이 마지막 받은 시각 이후인 줄만 받아 사본에 반영 ③ 실시간 구독: `room_msgs`·`room_members` 변경 시 ②와 같은 처리 ④ 오프라인이면 대기열(`damda:rpend`)에 남겼다가 연결되면 올리기 |
| C3 | `saveList` (2101줄) | 공유방이면 로컬 저장 뒤 `RoomSync.mark(방)` 호출. 서버 `members` 숫자 저장 로직 삭제 |
| C4 | 공유 버튼 `btnShare` (5642줄) | 로그인 안 했으면 "공유하려면 로그인하세요". 했으면 `rpc('create_room')` → 코드가 겹치면 새 코드로 재시도 → 기존 메모 전부 올리기 |
| C5 | 참여 `doJoin` (5683줄) | **방에서 쓸 이름 입력칸 추가**(기본값: 로그인 이름). `rpc('join_room')` → 빈 결과면 "방을 찾지 못했어요", 차단이면 "잠시 후 다시" |
| C6 | 권한 바꾸기 (5670줄) | `rooms` 표의 `perm` 수정 |
| C7 | 나가기 (2515줄) | `room_members`에서 내 줄 삭제 |
| C8 | 공유 시트 `shareWho` | 숫자 대신 **멤버 이름 목록** 표시 |
| C9 | 사진 올리기·받기 (1598·1699줄) | 공유방 메모의 파일이면 `r/방ID/파일ID` 경로 사용 (파일 객체에 `room` 표시) |
| C10 | 기존 공유방 옮기기 | 아래 5번 |

## 5. 기존 공유방 옮기기 (기획 T8)
로그인 후 한 번만(`damda:roomsMoved:계정ID` 표시) 실행한다.
1. **내가 만든 공유방**(`joined` 아님): `create_room(같은 코드)` → 메모 전부와 사진을 올림. 코드가 이미 있으면 새 코드를 받고 "코드가 바뀌었어요" 안내.
2. **내가 참여했던 공유방**(`joined`): `join_room(코드)`로 자동 재참여. 방장이 아직 안 옮겼으면 다음 접속 때 다시 시도.
3. 다 옮긴 방의 옛 `kv` 줄은 지움 표시.

[판단] 지금 실제 이용자가 팀원 몇 명뿐이라, 옮기기가 실패해도 피해는 작다. 그래도 지우기 전에 이 기기 사본은 남겨 둔다.

## 6. 제작 순서와 시험 방법
1. `rooms.sql` 문법·정책 시험 — 내 PC에서 브라우저용 Postgres(PGlite)로 표·정책을 만들어 보고, 가짜 사용자 3명으로 기획 T4·T5 같은 권한 시험 [판단: 가능 여부 제작 단계에서 확인]
2. `RoomSync` + C1~C9 구현
3. 옮기기(C10)
4. **실제 서버 시험**: 상현 님 운영 서버에 바로 넣지 않고, **시험용 Supabase 프로젝트**(무료, 계정당 2개까지 ✅ [요금](https://supabase.com/pricing))에서 폰 2대로 기획 T1~T8
5. 통과하면 상현 님께 PR + `rooms.sql` 실행 부탁

## 7. 남은 위험
| 위험 | 대응 |
|---|---|
| SQL을 아직 실제 DB에서 돌려 보지 않음 | 제작 1단계 PGlite 시험 + 시험용 프로젝트 |
| 같은 메모를 두 사람이 동시에 고치면 나중 사람이 이김 | 팀플 메모는 각자 쓰는 경우가 대부분이라 1바퀴는 감수 [판단] |
| 무료 프로젝트 1주 비활성 시 일시정지 | 발표 전 접속 확인 |
| 삭제 이벤트에 RLS 미적용 | 줄 삭제 대신 `deleted` 표시 — 단, 마지막 사람이 나가서 방이 지워지는 경우는 실제 삭제 (그 방 멤버가 아무도 없으므로 노출 위험 낮음 [판단]) |
| 시험용 Supabase에 카카오 로그인 설정이 또 필요 | 시험은 구글 로그인 또는 이메일 로그인으로 [판단] |
